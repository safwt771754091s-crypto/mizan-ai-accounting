# الرقابة الداخلية ومسارات الاعتماد (المرحلة 2)

المرحلة الثانية من خطة RAKAZ Enterprise. الهدف: ألا يصل أي رقم إلى القوائم المالية إلا عبر
مسار موثّق (إدخال ← إرسال ← اعتماد ← ترحيل)، وأن يكون كل إجراء حسّاس قابلاً للتتبع.

## 1. دورة حياة القيد

```
draft ──submit──▶ submitted ──approve──▶ approved ──post──▶ posted ──void──▶ void
  │                    │                                        ▲
  │                    └──reject──▶ rejected ──submit──┘        │
  └────────────────────post_direct──────────────────────────────┘
```

- `draft`: قيد غير مؤثر على الأرصدة، قابل للتعديل.
- `submitted`: أُرسل للمراجعة، ما زال غير مؤثر.
- `approved`: اعتُمد، بانتظار الترحيل.
- `posted`: الوحيد الذي يدخل ميزان المراجعة والقوائم.
- `rejected`: أُعيد لصاحبه مع سبب مكتوب، ويمكن إعادة إرساله.
- `void`: قيد مرحّل أُلغي؛ يبقى في السجل ولا يُحذف.

القواعد في `src/lib/accounting/workflow.ts` (`ALLOWED_FROM`, `checkTransition`) وهي دوال
نقية بلا اعتماد على واجهة أو قاعدة بيانات، لذلك تُختبر مباشرة.

### الضوابط المطبقة

| الضابط | التفصيل |
| --- | --- |
| لا ترحيل دون اعتماد | `post` مسموح من `approved` فقط. |
| ترحيل مباشر مقيّد | `post_direct` يحتاج صلاحية `journal.post` منفصلة عن `journal.submit`. |
| فصل المهام | من أنشأ القيد أو أرسله لا يعتمده ولا يرفضه. |
| الرفض موثّق | سبب الرفض إلزامي ويُحفظ في `review_note`. |
| الفترة المغلقة | تمنع `submit/approve/post/post_direct/void`، وتسمح بالرفض فقط. |
| لا حذف | لا يوجد أي مسار لحذف قيد من واجهة الاعتماد. |

## 2. الصلاحيات

| الإجراء | الصلاحية |
| --- | --- |
| إرسال قيد | `journal.submit` |
| اعتماد / رفض | `journal.approve` |
| ترحيل | `journal.post` |
| إلغاء قيد مرحّل | `journal.reverse` |
| إغلاق فترة | `periods.close` |
| إعادة فتح فترة | `periods.reopen` |
| عرض سجل التدقيق | `audit.view` |

التحقق يتم على الخادم في `src/app/actions/journal.ts` عبر `assertCompanyPermission`،
وإخفاء الأزرار في الواجهة مجرد تحسين تجربة لا يُعتد به كضابط أمني.

الأدوار النظامية: المالك والمدير يعتمدان؛ المحاسب الأول يرسل ويرحّل دون اعتماد؛
المحاسب يرسل فقط؛ المراجع والمشاهد لا يعدّلان.

## 3. الاستيراد والرقابة

`POST /api/import/confirm` يحدد حالة القيود المستوردة بحسب صلاحية المستخدم:

- من يملك `journal.post`: تُحفظ القيود `posted` كما كان سابقاً.
- من لا يملكها: تُحفظ `submitted` مع `submitted_by` و`submitted_at`، ولا تؤثر على الأرصدة
  حتى يعتمدها من يملك `journal.approve`.

كما يرفض الاستيراد (409) إذا وقعت أي قيود داخل فترة `closed` أو `locked`.

## 4. سجل التدقيق

جدول `audit_logs` إلحاقي فقط:

| العمود | المعنى |
| --- | --- |
| `company_id` | نطاق السجل |
| `user_id` | المنفّذ |
| `action` | مثل `entry.approve`, `period.close` |
| `entity`, `entity_id` | الكيان المتأثر |
| `from_status`, `to_status` | انتقال الحالة |
| `note` | سبب الرفض أو إعادة الفتح |
| `meta` | رقم القيد، اسم الفترة، المبلغ |

سياسات RLS: قراءة لمن يملك `audit.view`، وإلحاق لعضو الشركة بشرط `user_id = auth.uid()`،
ولا توجد سياسة تحديث أو حذف، مع `revoke update, delete` عن `authenticated`.

## 5. الواجهات

- `/approvals` — قائمة العمل: مسوداتك، بانتظار الاعتماد، معتمد بانتظار الترحيل.
- `/periods` — حالة الفترات، عدد القيود المعلّقة، إغلاق وإعادة فتح.
- `/audit` — آخر 200 إجراء مع المنفّذ والانتقال والملاحظة.

كلها تعتمد `loadCompanyContext` وتُخفي محتواها عند غياب الصلاحية.

## 6. ما لم يُنفَّذ بعد

- مسار موافقة متعدد المستويات (approval chains) وتفويض مؤقت.
- إشعارات بريدية عند الإرسال والاعتماد.
- قفل الفترة نهائياً (`locked`) من واجهة المالك.
- اختبارات RLS على Supabase حقيقي (البيئة الحالية demo).
